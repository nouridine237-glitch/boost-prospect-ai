- Keep onboarding in a shared authenticated-layout provider with profile-backed flags and user-scoped activity reads, so welcome appears across entry pages and dismissal persists across devices.
- Store the shared scripts library in public.scripts with authenticated reads and admin-only writes enforced by RLS; load it with user-scoped query options and pass script IDs to the existing AI function so personalization shares quota enforcement and uses owner-scoped prospect context.
- Keep public landing visuals and motion scoped to lp-prefixed classes and illustrative components, preserving authenticated screens and pricing logic; derive every landing plan figure (cards, comparison table) from the plan/feature constants via src/lib/landing-content.ts (tested) instead of retyping them. Use CSS transform/opacity with one IntersectionObserver and a static optimized share image. Why: lightweight rendering and no drift between marketing copy and real limits.
- SasPay online payments: prices are fixed server-side in saspay.server.ts; webhooks only trigger a re-verification via GET /checkout-sessions/{id}/status/ and the conditional en_attente→valide update is the single activation path (idempotency). Why: webhook payloads are never trusted to activate a plan.
- MCP server lives in src/lib/mcp (one tool per file, OAuth via Lovable Cloud auth, RLS as caller). Why: external assistants act as the signed-in user without privileged keys.
- Referral rewards are granted only by SECURITY DEFINER triggers (first prospect insert, subscription turning paid); client reads only, claim/code creation via server functions. Why: no reward can be triggered from the browser.
- Academy quiz results are scored server-side (`scoreQuiz` in academy.functions.ts) and written only via service-role `record_academy_result` (keeps best score). Leader–member links live in `team_links` (not `referrals`), changed only through SECURITY DEFINER `team_*` functions; leaders read members solely through `team_member_progress()` aggregates. Why: browser scores are untrusted and members' private data must stay private.
- Duplication catalogue is app-managed in a server-only versioned module, delivered only after effective-plan gating; own checklist progress uses duplication_progress and its authenticated SQL writer with ordered days and immutable completed entries. Why: paid content must not ship in free bundles and cross-device progress must not expose member data.
- Video lesson progress lives in `academy_lesson_progress` (owner SELECT only); written solely via service-role `record_lesson_progress` after plan/publication checks, with watched time credited by the server clock between consecutive "playing" reports. Why: opening a lesson or a forged client report must never mark it complete.
- Command center (src/lib/command-center.ts) is a pure local intent router and daily brief: it only links to existing tools, never calls AI, never sends messages, and reuses existing plan gating. Why: orientation must cost no quota and add no new access path.
- Conversation simulator (src/lib/simulator.ts pure rules + simulator.functions.ts): open to all plans, each prospect reply and the review reserve one generation via reserve_ai_generation (refunded on failure); transcript lives only in browser state, no table. Why: training must share existing quota enforcement and never contact real prospects.
- Status planner: user-owned rows in content_posts (owner-only RLS, no anon); a BEFORE trigger is the source of truth for weekly limits by effective plan, required text and server-set published_at; generation reuses generateProspectingContent in Post mode. Why: client checks are untrusted and AI quota must stay shared.
- Campaign tracking: owner-only `campaigns` table; nullable links content_posts.campaign_id and prospects.campaign_id/source_post_id checked by SECURITY DEFINER triggers (same owner, published source, free-plan active limit); metrics are pure in src/lib/campaigns.ts. Why: attribution is manual and never inferred, so figures stay real.
- Action plan (30 days): owner-only `action_plans` + `action_plan_weeks` store targets only; actuals are always recomputed from prospect_events/content_posts/prospects via pure src/lib/action-plan.ts (reuses weeklyRecap). Paid-only via FEATURE_MIN_PLAN.actionPlan and SECURITY DEFINER guards on effective_plan (one active plan, Monday start, reviewed weeks immutable). Why: no result can be typed or forged, and gating stays in the single existing plan system.
- Video library: private `user-videos` bucket (owner-folder insert for a declared `envoi` row only); plan quotas in `user_videos_guard`; playback via 1 h server-signed URLs after `lessonAccess`. User courses reuse academy_courses/lessons (owner_id set; catalog filters `owner_id IS NULL`). Sharing = `course_grants` pinned to immutable `course_versions`, written only by SECURITY DEFINER `grant_*` (one reshare level, revoke within 7 days of acceptance, no share with an unavailable video); access never depends on plan or team_links. `moderate_video` (via transaction-local `vt.trusted_op`) disables only its lesson; `moderate_course` is separate. DB scenarios: scripts/test-sharing.sql. Why: durable access, private files never public.
- Duplication Hub: `/d/$token` reads only via duplication-hub.functions.ts (hashed token, allowlisted fields, one free lesson, 10-min signed URL); sign-in grants nothing beyond course_grants. Why: anon never reaches private data.
- `prospect_events` is append-only with server `created_at` (trigger). Why: sole activity source for team indicators.
- Admin Ad Studio: require the principal UUID, existing admin role and verified aal2 session in server handlers and RLS; only the MFA gate may use aal1. Preserve original analyses and append-only note revisions with optimistic version checks. Keep web analysis disabled until transport SSRF guarantees are verified. Why: UI restrictions and pre-fetch DNS checks alone are insufficient; general admin rules stay untouched.
